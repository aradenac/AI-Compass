## Shared record and interaction component contract

`AICompassWorkgroup.renderRecords(records, {domain, mode})` provides one escaped card/metadata/action/link DOM across Demo and Server. Callers **must** pass explicitly authorized rows, labels, untrusted values as plain text, and only action attributes delegated by their original permission-aware controller. Links are restricted to relative same-origin routes; never silently convert an API failure into Demo content. The component deliberately knows nothing about source data or write authorization.

`renderCampaignMatrix`, `renderMatrixCellDetail` and `renderMatrixDecisionFields` provide one evaluation-matrix presentation: strict projection validation (exact revision, known cell states/decisions, waiver with reason, same-origin links), shared counters, the explicit "Waived / Not Selected / Pending are never measured evidence" notice, the pinned Test Case revision and the measured Runs of one cell. A cell detail links to the **exact pinned Test Case revision** it evaluated, never to the current one, and lifecycle transitions are offered only while the displayed plan revision is the current campaign revision (a historical plan is explicitly read-only). Demo and Server only differ in the authorized rows and routing they supply.

`renderDomainFields(spec, values, mode)` renders one ordered field presentation per domain from an authorized specification (`WATCH_SOURCE_FIELDS`, `WATCH_ENTRY_FIELDS`, `FORECAST_FIELDS`, `FEEDBACK_THREAD_FIELDS`, `FEEDBACK_REPLY_FIELDS`, `RECOMMENDATION_FIELDS`, `EVALUATION_FIELDS`, `GUIDE_RECIPE_FIELDS`) with explicit Demo/Server keys, vocabularies and mode-only inputs; the same renderer supports permission-locked fields (a hidden value instead of a control the role may not choose). `renderDomainDetail`, `renderThread`, `renderStepper`/`campaignLifecycleSteps`, `renderLifecycleActions`/`campaignLifecycleActionKeys`, `renderMeasuredRunDetail`, `renderObservationMatrix`, `renderComposedSetup` and `renderDomainStatus` do the same for record detail, conversation threads, lifecycle steps, review/publication transitions, one measured Run, the comparison matrix, the composed pinned-module setup and loading/read/refused/denied status. Dialog focus belongs to the same contract: opening moves focus inside the dialog and closing returns it to the control that opened it, in Demo and Server alike.

Shared cards also bound the action column so that a domain exposing many permitted actions can never squeeze the record content: a real defect found while inspecting Server screenshots (the campaign page was 28 000 px tall and is now readable).

This converges **presentation and interaction primitives, not business models**. Documented intentional differences: Demo has no saved-Evaluation object (Server-only specification), Demo fixtures carry no per-Run immutable revision (Server Runs keep their effective revision), Demo validations stay local messages while Server marks required inputs natively, the Server recipe/metadata JSON fields have no Demo counterpart, and campaign/session *controllers* (data access, RBAC, persistence) remain mode-specific. No unsupported Server action is mocked and no Demo fixture is presented as a Server record.

## Verification crosswalk

- JavaScript unit checks: `node scripts/test-shared-case-tree.js`, `node scripts/test-shared-campaign-matrix.js`, `node scripts/test-shared-domain-primitives.js`, `node scripts/test-campaign-matrix.js`, `node scripts/test-workgroup-studio.js`, existing Server controller suites, `node scripts/test-shared-frontend.js`. Shared component tests assert Demo/Server DOM parity for equivalent authorized rows, hostile-text escaping, unsupported/absent modes, unknown states, waiver-without-reason, non-privileged actions, fork cycles and same-origin link rejection.
- Real browser: `python scripts/ux_qa.py provision --output /tmp/ux-qa-credentials.json` on a disposable composed Server, followed by `python scripts/ux_qa.py test --base-url http://127.0.0.1:8080 --demo-url http://127.0.0.1:8090/prototype.html --credentials /tmp/ux-qa-credentials.json --artifacts /tmp/ux-qa`. The suite checks shared Demo domain cards, complete Test Case field persistence, real Server domain presentations, a real authorized Server Task → Test Case creation/reload, and the shared campaign matrix in both modes: Demo plans a configuration and records a waiver through the shared decision form, Server creates a real catalog trio + campaign + configuration, records the same waiver and proves it survives a full browser reload. The same journeys now also prove negative behaviour in real browsers: a **stale plan revision** and a **stale task move** are refused with explicit revision messages through the shared status presentation (HTTP 409, never silently applied, and the refusal survives the follow-up reload), an **unavailable domain API (503)** fails closed with the shared error status and no Demo substitution, and an **Engineer session cannot reach the Workgroup Test Case editor** (fail-closed, one active view). Both modes must offer exactly the same canonical campaign lifecycle transitions, and the Demo Forecast detail must expose the shared review bar with its theoretical provenance notice. Modal/role/context journeys remain covered.
- **Not yet proof:** Recommendations detail and their review/withdraw lifecycles, running correction/withdrawal of a published Run, Test Case fork/evidence denial round trips, the Demo organizer's drag-and-drop versus the Server up/down move affordance, full keyboard order beyond dialog focus return, the full §13 multi-role scenario matrix, removal of the remaining duplicated detail DOM, and 1366×900 screenshot approval by a reviewer. An unavailable domain API is now proven to fail closed (503 shown through the shared status presentation, no Demo substitution), and stale plan/task revisions are proven to be refused explicitly. Until those are demonstrated, no claim of complete UX-R04 acceptance, TD-01 closure, production staging GO or safe resumption of P7.

Existing Django integrity, revision, CSRF/RBAC, migration and recovery CI are independent mandatory gates. Mobile/tablet acceptance and enforcing branch-rule TD-UI-01 remain deliberately out of scope.
